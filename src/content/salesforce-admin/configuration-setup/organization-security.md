## The controls in this module

Organization security controls protect the Salesforce login/session environment. The major controls covered are:

| Control | Answers |
|---|---|
| Setup Audit Trail | Who changed the configuration? |
| Password Policies | How strong must passwords be? |
| Session Settings | How does a session behave once created? |
| Login Hours | **When** can users log in? |
| IP Restrictions | **From where** can users log in? |
| Trusted IP Ranges | Which networks are trusted? |
| Device Activation | Is this an unfamiliar device/browser? |
| MFA | Is there a second authentication factor? |
| SSO | Is authentication centralized? |
| Login History / Forensics | What happened during login attempts? |
| Security Health Check | How secure is the configuration overall? |

## Setup Audit Trail

**Who changed the Salesforce configuration?** Setup Audit Trail answers **who + what + when** for administrative/configuration changes.

An administrator wants to know who changed a profile, who modified a configuration, or who changed a setup setting → **Setup Audit Trail**.

## Password Policies

Password policies can be configured to improve password security. Relevant areas include:

- Password requirements
- Password expiration
- Password history
- Lockout-related behavior
- Password strength/security settings

### Exam shortcut

> "The administrator wants stronger password requirements."

Think: **Password Policies.**

## Session Settings

Session Settings control security-related behavior **after** a user has established a Salesforce session. They can be configured at organization/profile-related levels, depending on the setting.

```sequence
Login
Session created
!Session Settings control session behavior
```

### Exam shortcut

The question is specifically about the behavior/security of the Salesforce **session** → **Session Settings**.

## Login Hours

**When can users log in?** Login Hours are configured through the **profile**.

```text
Monday–Friday
9:00 AM – 6:00 PM
```

Users with that profile are restricted according to the configured login hours.

### Memory trick

**WHEN = Login Hours**

## IP Restrictions

**From where can users log in?** Profile-level login IP ranges can restrict access to specified IP ranges.

```text
Allowed:  Company Network
Denied:   Outside IP Range
```

### Memory trick

**WHERE = IP Restrictions**

## Trusted IP Ranges

Organization-level trusted IP ranges can be configured through **Network Access**.

Users logging in from a trusted IP range can avoid an identity verification challenge. If a user logs in outside the trusted range, an activation/verification challenge can occur, according to the configured security behavior.

| Trusted IP Range | Profile Login IP Range |
|---|---|
| Organization/network-level concept | Profile-level restriction |
| Trusted locations | Allowed login IP ranges |
| Helps determine whether a login challenge is required | Can deny login outside allowed ranges |

### Gotcha

Don't mix these up: a **trusted IP range** decides whether a user gets a verification challenge; a **profile login IP range** can **deny** the login entirely.

## Device Activation

Device Activation adds another security layer beyond username and password. It can be triggered when a user logs in from an **unrecognized browser/device** and is **outside a trusted IP range**.

Verification can use methods such as email, SMS, Salesforce Authenticator, or built-in authenticators/biometrics.

```flow
Username + Password
Recognized / trusted?
Yes → Login | No → Identity verification
```

## Salesforce Authenticator

Salesforce Authenticator can be used for identity verification/MFA-related workflows. If push notifications are unavailable, the source material notes that users can use **time-based one-time passcodes** generated by the authenticator app in supported scenarios.

## Built-in authenticators

Built-in authenticators use the device's biometric mechanism to verify identity — for example **Touch ID, Face ID or Windows Hello**.

## Multi-Factor Authentication (MFA)

MFA requires more than one authentication factor:

```flow
Something you know | Something you have / are
!Stronger authentication
```

For example: **Password + Salesforce Authenticator**, or **Password + Security Key**.

### Exam shortcut

> "Require a second verification method."

Think: **MFA.**

## Single Sign-On (SSO)

SSO allows Salesforce authentication to be integrated with an external **identity provider**. The source material discusses federated authentication such as **SAML** and **delegated authentication**.

```flow
User
Identity Provider
Salesforce
```

The user can use centralized identity management rather than maintaining separate authentication for every application.

## Login History

Login History is useful for investigating login attempts — successful attempts, failed attempts, time/date and other login-related information.

### Scenario: Someone tried to get in

**Situation:** A user says someone may have attempted to access their account.

**Recommended concept:** **Login History.**

**Why:** It shows successful and failed login attempts with their date and time.

## Login Forensics

Login Forensics is intended for **deeper** analysis of login-related event information.

| | Use for |
|---|---|
| **Login History** | Basic login investigation |
| **Login Forensics** | Deeper login event investigation |

## Security Health Check

Security Health Check helps identify potential vulnerabilities and compares security settings against a **security baseline**. The source describes a summary score based on how the organization's settings compare to the baseline.

```sequence
Current security settings
Security Health Check
Compare with the baseline
!Find risky settings
```

### Exam shortcut

> "The admin wants to evaluate the overall security posture of the Salesforce org."

Think: **Security Health Check.**

## Memory tricks

```text
WHEN        = Login Hours
WHERE       = IP Restrictions
TRUSTED     = Trusted IP
WHO ARE YOU = MFA / Device Activation
SESSION     = Session Settings
```

- **Login History** = user login activity · **Setup Audit Trail** = configuration changes.

## Before exam

- Login Hours and login IP ranges are set on the **profile**; trusted IP ranges are set org-wide in **Network Access**.
- Outside a trusted range on an unrecognized device → **Device Activation** challenge.
- "Second verification method" → **MFA**. "Centralized login with an identity provider" → **SSO**.
- "Who changed setup?" → **Setup Audit Trail**. "Failed login attempts" → **Login History**.
- "Security score / baseline" → **Security Health Check**.
